## 1. Target and the date that drives the order

The next newsletter is the **October 2026 edition, due Monday 2 Nov 2026** (first working day of November; the
September edition went out on 1 Oct). It must be producible **by hand with today's flow** even if nothing below is
merged, so nothing here can block it. What this plan adds is: the redesigned Indonesian email, recommended articles
already placed in the composer, and an Executive Summary drafted from weekly recaps.

For the Executive Summary of the 2 Nov edition, weekly recaps for **28 Sep - 1 Nov** must exist (5 weeks, 5 LLM
calls). Four of them (the weeks starting 28 Sep, 5, 12 and 19 Oct) are generated by hand after the deploy (a backfill).
The fifth (26 Oct - 1 Nov) can only be generated once Sunday 1 Nov has ended in UTC, so it comes from the **scheduled
run on Monday 2 Nov at 07:15 WIB**, before the newsletter is prepared at 09:00 WIB. The weekly recap (PR 2) therefore
has to be **deployed, with `beat` restarted, by Fri 30 Oct at the latest**; the target is a week earlier so someone can
read the first output on the Recap page.

## 2. Ground rules for every PR

- One PR per slice below, each mergeable and revertible alone, each with its own tests. Branch from `main`.
- Hand-written alembic migration plus the model change in the same PR (`test_migrations_match_models`). Migrations
  are additive (new nullable or defaulted columns, new tables); nothing is dropped except the one unique constraint in PR 2.
- **New settings have safe defaults** and `.env.example` + `.env.prod.template` change in the same commit
  (`test_config`, `test_env_prod_template`). A required key would make the prod app refuse to start and roll the deploy
  back (CLAUDE.md, Deployment), so no setting is required.
- **Removing a setting is just as dangerous**: `extra="forbid"` rejects a key that is still in the prod `.env` once its
  field is gone (checked 2026-10-11: an unknown `LLM__*` key fails with `extra_forbidden`). A field is deleted only after
  its key has been removed from the prod `.env`, `.env.example` and `.env.prod.template`, in an earlier release.
- API changes: `uv run python tools/export_openapi.py` and `cd apps/web && pnpm run gen:api` in the same PR (CI drift check).
- Gates before pushing: `ruff check`, `ruff format --check`, `mypy` (strict, `cti-core` and `cti-scraper` only), unit +
  contract tests, and the integration tests for what changed. Web PRs: lint, `next typegen` + `tsc --noEmit`, build.
- Code comments, docstrings and commit messages in Indonesian, docs in English (CLAUDE.md). Releases bump the version
  files and `CHANGELOG.md` (Indonesian): one release after #21 (0.5.0) and one after #22 (0.6.0).
- LLM calls always go through one helper that records token usage (PR 1), so every later PR logs usage for free.

### PR 2 - Weekly recap (#21) - size L

- **Migration**: `daily_recaps` gets `kind` (`weekly`|`daily`, default `daily`), `period_start` and `period_end`
  (`Date`). Backfill existing rows: `kind='daily'`, both dates = `date`. Replace `uq_daily_recap_date` by a unique
  constraint on `(kind, date)`; for a weekly row `date` is the **Monday** of the week. The table name stays
  (`daily_recaps`), renaming it is not worth the churn.
- **Reads take the kind**: `AsyncRecapRepo.get` and `upsert` take `kind`. Today `get(date)` uses
  `scalar_one_or_none()`, which raises `MultipleResultsFound` (a 500) as soon as a daily and a weekly row share a Monday.
- **Window**: Monday-Sunday by the **calendar dates the collectors already use** (`posted_on`, `func.date(...)`), which
  are UTC dates. That fixes the generation time: the week is only complete once Sunday ends in UTC, so the beat entry is
  **Monday 00:15 UTC = 07:15 WIB**, not 00:15 WIB (a 00:15 WIB run would miss Sunday 17:00-24:00 UTC). The newsletter
  task (09:00 WIB) still runs after it. The DB session timezone must be UTC for `func.date(timestamptz)` to mean what
  this assumes: a test or startup check asserts it.
- **A week is generated only after it has ended**: `generate_weekly_recap` refuses a week whose Sunday has not ended in
  UTC (HTTP 400 from the router). Otherwise a hand run on, say, Friday 30 Oct would store an incomplete week, and the
  scheduled run on Monday (`force=False`) would return that cached row instead of the full week.
- **Collectors**: the single-day repo methods (`list_registered_on`, `list_first_seen_on`, `list_added_on`, tweets)
  get range variants (`..._between(start, end)`). `AsyncArticleRepo.list_filtered` already takes a date range.
- **Campaigns by window**: `campaign.get_recent_campaigns` counts back from `datetime.date.today()` (`days=7`), so a
  backfilled week would get the campaigns of the week it is run in, not its own. Add optional `start`/`end` (dates) to
  it, keep `days` for the current callers, and pass the recap window here (PR 7 and PR 8 reuse it for the month). It
  reads at most 2000 articles: log a warning when that cap is hit, and check the monthly article volume before PR 8.
- **Aggregates, not a wider prompt**: per category take the top N by signal (confidence/score, confirmed incident,
  KEV/PoC, source reliability, cluster size), plus per-category counts via `GROUP BY`, and clusters collapsed to one
  line. The prompt grows far less than 7x. Output language stays **English**; forecast horizon becomes 1-2 weeks;
  `top_stories` caps are raised only as far as the baseline allows.
- **No-activity path**: a week with nothing to summarise stores a row with empty content and makes **no LLM call**.
- **Service/API**: `generate_weekly_recap(session, week_start, force)`; `POST /api/recap/generate` gets `kind` and
  `week_start` (a day can still be generated by hand: `kind=daily`, `date=`, unchanged). `GET /{date}` gets a `kind`
  query parameter (default `daily`, the date picker's meaning); `GET /list` returns both kinds with `kind` and the
  range; `GET /latest` returns the latest **weekly** row (today it assumes "yesterday").
- **Recap page (small web change in this PR)**: the page opens on the latest weekly recap (today it opens on
  yesterday's date), the history lists both kinds with their range and fetches each with its kind, and the title reads
  "Weekly Recap · 28 Sep - 4 Oct" or "Daily Recap · <date>". The date picker still generates a single day. Deltas,
  grounding and the scorecard stay in PR 4. Why here: the weekly recaps must be readable on the page before 2 Nov (the
  Executive Summary may be written by hand from them if PR 8 is late), and once the page opens on the weekly recap the
  daily schedule has no reader left.
- **Beat**: add `recap.generate_weekly` on Monday 00:15 UTC (`crontab(day_of_week=1, hour=0, minute=15)`, queue
  `maintenance`) and **remove the `recap-generate-daily` entry** in the same PR (ROADMAP: no scheduled daily recap). No
  setting: the manual daily trigger stays, the weekly entry is additive, and rollback is reverting the PR (the migration
  is additive). Beat builds its schedule at import, so `beat` must restart after the deploy.
- **Backfill** (needed for 2 Nov): after the deploy, generate the weeks starting 28 Sep, 5, 12 and 19 Oct by hand. The
  week starting 26 Oct comes from the scheduled run on Monday 2 Nov.
- Tests: unit for the window (week containing a month/year boundary, Monday start), the refusal of an unfinished week,
  the aggregate builder and the no-activity path; integration for the migration backfill, the unique `(kind, date)` rule
  (a weekly and a daily row on the same Monday coexist and both are readable by kind), the range collectors, the
  campaign window, the beat schedule (weekly entry present, daily entry gone) and the router snapshots (update with
  `--snapshot-update` after reading the diff). Web: lint, `tsc`, build.

### PR 3 - Recap quality: comparison, grounding, scorecard (#21) - size M

- **Migration**: add `quality` (JSONB, default `{}`) to `daily_recaps`.
- **Week-over-week comparison** (no LLM): `counts` of this week against the previous weekly row as absolute and
  percentage deltas, plus "new this week" for threat actors, campaigns and CVEs (set difference with the previous
  week's stored items). Stored in `quality.comparison`.
- **Grounding check** (no LLM): after parsing, every CVE id, threat actor, campaign theme and source in the output must
  exist in the input sets used to build the prompt. **Stories are checked by id, not by title**: the model paraphrases
  titles, so an exact title match would drop real stories. Each article line in the prompt carries its id (`[#123]`),
  `top_stories` returns `article_id`, and a story stays only if that id was in the input; the stored story then carries
  the article URL so the page can link it. Anything that fails is **removed from the displayed fields and listed** in
  `quality.grounding.dropped` (field, value), with the count. Nothing is dropped silently. The same function is reused
  by the newsletter summary (PR 8), so it lives in a shared module, not in `recap.py`.
- **Forecast scorecard** (same call, no extra call): each stored `likely_events` item gets an id (`f1`, `f2`, ...). The
  weekly prompt also receives last week's events with their id, `basis` and `confidence`, and returns `forecast_review`
  (verdict `happened | partly | not_happened | unclear` plus one line of evidence per id, the labels ROADMAP #21 uses).
  Code stores it in `quality.scorecard` and computes the hit rate over the last 8 weeks, split by confidence
  (recommended: `partly` counts as half, `unclear` is left out of the denominator).
- **Analyst override** (ROADMAP #21): `PATCH /api/recap/{id}/scorecard/{event_id}` sets a verdict; it is stored next to
  the model's verdict (who, when), the hit rate uses the analyst's verdict when there is one, and the call is written to
  the audit log like `generate`.
- Tests: unit for the comparison (first week with no previous row, a CVE that appears twice), for grounding (an invented
  CVE id is dropped and listed; a real one stays; case and spacing; a story citing an id that was not in the input is
  dropped), for the scorecard maths with a stubbed LLM, and for the override changing the hit rate.

### PR 5 - Newsletter foundation (#22) - size L

All of it is invisible to readers, and it removes the defects found while scoping.

- **Summary cache**: new table `newsletter_article_summaries` (`article_id`, `language`, `key_points` JSONB, `summary`,
  `body_source`, `iocs` JSONB, `cve_ids` (the CVE ids found in the title and body), `model`, `token_usage`,
  `created_at`; unique `(article_id, language)`). `generate_article_summary` reads it first; a hit makes no Playwright
  fetch and no LLM call. A `regenerate` flag per article bypasses it. `iocs` and `cve_ids` are cached because they come
  from the fetched body: without them the draft step would have to fetch the page again to write IOCs.
- **Preview without side effects on the record**: `preview` builds from the cache, **creates no `newsletters` row and
  writes no IOCs or CVE mentions** (today it does all three). It still writes the two caches: the summary cache on a
  miss, and the paywall hint that `fetch_article_body` already upserts. Test: preview twice, then draft, and count rows
  (exactly one) and LLM/Playwright calls (zero on the second preview and on the draft).
- **One send, one row, in this order**: build from the cache, call `create_graph_draft`, then save the row, upsert the
  cached IOCs and write the CVE mentions (`cve_ids` intersected with the true-positive set at that moment), then commit.
  Today `_build_and_save` commits before the Graph call, so a failed Graph call leaves a history row without a draft. If
  the save fails after Graph succeeded, the draft exists without a row: log the Graph message id.
- **Period columns**: `period_start`, `period_end` (`Date`, nullable) on `newsletters`. `week`/`year` are `NOT NULL`:
  new rows keep filling them (ISO week of the generation time, as today), so no constraint changes and the current
  history UI keeps working. The history list returns the derived label ("October 2026") when the period is set, else
  "Week N, YYYY".
- **Where the period comes from**: the build request gains optional `period_start`/`period_end`; the default is the
  previous calendar month of today's local date (offset `WORKER__REPORT_UTC_OFFSET_HOURS`, WIB). A hand-built edition
  (2 Nov without PR 8) gets the right month without a web change.
- **Tiers**: the request schema gains `highlights: list[int]` and, per section, `full: list[int]` and
  `compact: list[int]`; limits move from "5 per section" to **full <= 4 (Highlights <= 3) and compact <= 15** (constants
  in one place, tuned after the first edition). The old fields stay accepted until PR 9 ships so the web does not break
  between PRs. Compact entries are built from the article row (no fetch, no LLM; a cached summary is used if present).
- Tests: unit for the cache hit/miss, the limits, the tier split and the default period; integration for the one-row
  rule (a failing Graph call leaves no row; the draft writes the cached IOCs without a fetch) and the router snapshot.

### PR 7 - Ranking and suggestions API (#22) - size M

- `services/newsletter_ranking.py`: a **pure function** over candidate rows (the articles of the window) returning, per
  article, a score, a section (APAC / Global / Indonesia), a tier and the list of **reasons**. Signals: confidence score,
  confirmed incident, KEV/PoC on mentioned CVEs, a hit on a monitored tech (#19) or on a client country, source
  reliability, cluster size (from the window-aware `get_recent_campaigns`, PR 2), APAC/Indonesia relevance; duplicate
  stories collapsed (reuse `services/dedup.py` and `services/cluster.py` where they fit instead of a new similarity
  routine).
- **Client signals**: the newsletter is global, so they use the union over all clients: any client's country
  (`client_countries`) among the article's victim or mentioned countries, and any client's active techstack/catalog
  entry. Clients have **no industry field**, so there is no industry signal (adding one is not in this scope).
- **Migration**: `newsletter_suggestions` (`period_start`, `period_end` unique, `items` JSONB of `{article_id, section,
  tier, rank, reasons}`, `summary_text`, `summary_meta` JSONB, `created_at`). No status column (not selected).
- API: `GET /api/newsletter/suggestion` (latest, or by period) and `POST /api/newsletter/suggestion/rebuild` (auth,
  rebuilds a window by hand, the Executive Summary included once PR 8 exists; also what an analyst uses if the scheduled
  run was late or the last weekly recap arrived after it).
- Tests: unit for the ranking with hand-made candidates (each signal changes the order; duplicates collapse; reasons
  are listed; caps respected); integration for the repository and the router snapshot.

### PR 8 - Monthly schedule and Executive Summary (#22) - size M

- **First working day = the first Monday-Friday of the month**; public holidays are not tracked (user, 2026-10-11), so
  there is no holiday list and no new setting. When that day is a holiday (1 Jan 2027 is a Friday), the suggestion is
  simply ready before the analysts are back; nothing is sent automatically, so preparing early costs nothing.
- A pure function `first_weekday(year, month)` and `should_prepare(today, has_suggestion_for_previous_month)`, true
  when **today is within 7 days of the month's first weekday and the previous month has no suggestion yet**. The beat
  runs only on weekdays, so its first run in a month is that first weekday; the following days are the catch-up when
  the worker was down; the 7-day limit stops a mid-month deploy from creating a suggestion for a month that was already
  sent. After the window, only the manual rebuild.
- **Beat**: `newsletter.prepare_monthly` every weekday at 09:00 WIB, queue `maintenance`. `local_to_utc_cron` takes a
  single weekday, so the entry uses the hour and minute from `local_to_utc_cron(9, 0, offset)` (02:00 UTC) with
  `day_of_week="1-5"`; 09:00 WIB does not cross midnight in UTC, so the weekday range does not shift. The task calls
  `should_prepare`; if false it returns at once. One suggestion per window makes it idempotent, and a duplicate delivery
  (`acks_late`) costs at most one extra LLM call.
- **Preparation**: build the candidate list for the previous calendar month, run the ranking, store the suggestion;
  then the **Executive Summary**: read the weekly recaps that **exist and overlap the month**, one LLM call producing
  one Indonesian paragraph (about 100-130 words, no recommended actions), run the shared grounding check on it, store the
  text, the weeks used (`summary_meta.weeks`) and the usage. No recaps for the window means an empty summary field and
  no call.
- **The tail of the month**: when a month does not end on a Sunday, its last days fall in a week that is not finished
  on the first working day (November 2026 ends on Monday 30 Nov; that week ends 6 Dec, after Tuesday 1 Dec). Those days
  are not in the summary; they are still in the article ranking. The composer shows the range the summary covers. No
  daily recap is generated to fill the gap (one to six extra calls for little gain).
- Tests: unit for `first_weekday` (month starting on a Saturday and on a Sunday, year change) and for `should_prepare`
  (runs on the first weekday, the catch-up inside the window, nothing after it, the idempotent second run); the summary call with a stubbed LLM and recaps (grounding drops an invented CVE; no
  recaps means no call; the weeks used are recorded); a test that the beat entry exists and maps to 02:00 UTC
  Monday-Friday.

## 5. Cross-cutting

| Concern | Plan |
|---|---|
| LLM cost | Recap: one call per week (was seven) with a smaller input; scorecard and comparison add no calls. Newsletter: one call per cached article instead of per build, none for compact rows, plus one call per edition for the summary. Every call records usage (PR 1). |
| Rollback | PR 2: revert the PR and restart `beat` (the daily entry comes back; the migration is additive). PR 8: remove the beat entry or set the task to no-op; the composer works without a suggestion. Migrations are additive, so reverting the code leaves harmless columns/tables. |

## 6. Risks

- **Deploy is unproven**: Deploy runs #8-#10 were all `cancelled` (ROADMAP #13). If merges to `main` do not reach the prod
  host, PR 2 will not be live by 30 Oct: neither the backfill nor the scheduled run on 2 Nov happens. Check the host

## 0.8.10 — Admiralty confidence and priority per article (P6)

Applies on top of the 0.8.3 → 0.8.9 steps in `docs/PROD_UPGRADE_0.8.2_TO_0.8.9.md`; prod goes
0.8.2 → 0.8.10 in one `make deploy` (host `privy-admin@10.8.20.78`, compose project
`niskala-intelligence`: Postgres backup, `migrate` first, then waits for health, auto-rollback of
images on failure).

**Not yet run on dev.** P6 has not been deployed to the dev instance, so there are no dev runtime
numbers (migration time, recompute time, live distributions). Every number below comes from the
dev snapshot replay (`tests/fixtures/confidence_replay/dev_2026-10.csv`, 1,546 dev articles,
exported 2026-10-26) or is marked **projection**.

Helpers used below (run from the repo checkout on the prod host; user/db from `docker/stack.env`,
default `cti`/`cti`):

```bash
dc() { docker compose --env-file docker/stack.env --profile app "$@"; }
# read-only SQL: wraps the query in a READ ONLY transaction
psqlro() { dc exec -T postgres psql -U cti -d cti -v ON_ERROR_STOP=1 \
  -c "BEGIN READ ONLY" -c "$1" -c "ROLLBACK"; }
```

### What changes in prod

- Article confidence becomes pure Admiralty, computed per article by `cti_core.confidence.assess`:
  reliability A-F = source grade (`F` if the source has no row), credibility 1-6 from story
  corroboration, primary vs aggregator source (`content_kind`) and artefacts (CVE, non-suppressed
  IOC, explicit TTP). `confidence_score` = STIX 2.1 Admiralty scale averaged over both halves,
  always **10-90** (before: LLM self-rating on 0.8.2, source grade + bonus on 0.8.6-0.8.9, many at 100).
- New stored `priority_score` (confidence + incident/KEV/PoC/TTP/actor/corroboration points,
  uncapped) drives `sort=priority`: dashboard "Perlu dibaca" and the Newsroom front section show
  **one article per story**.
- Multi-release interaction: the 0.8.6 source-grade + bonus formula never runs on prod. The API
  start does a single `confidence.recompute_all` enqueue (condition: new default grades inserted
  **or** any article with `credibility IS NULL`), and that task now runs `assess`.
- An article whose `overrides` has `confidence_score` keeps that confidence; credibility and
  priority are still computed. `overrides.credibility` is new (set via
  `PUT /api/articles/{id}/credibility`, `manage_intel`).
- New beat entries (beat restarts on deploy): `confidence-refresh-stories` every 10 min,
  `confidence-recompute-all` daily 03:20. Both on the `maintenance` queue.
- New API: `GET /api/sr/review`, `POST /api/sr/entries/{id}/confirm` (`manage_sources`);
  `ArticleOut.admiralty_code` is now the article's code (plus `reliability_grade`, `credibility`,
  `priority_score`, `score_reasons`).
- Web: chip `C1 · P131` on dashboard, Newsroom front + list, article modal ("Why this grade",
  credibility override); Source reliability "Needs review" tab.

### One-off commands (recompute/backfills: exact command, `--dry-run` first, expected numbers from dev, how long; mark each as needing the user's approval)

Normally **none**: the API start enqueues `confidence.recompute_all` by itself. Run the following
only if after-deploy check 2 shows `recompute_all_enqueue_failed` or check 3 stays above 0.

There is **no `--dry-run`** for the recompute (it is idempotent and respects analyst overrides).
Read-only preview instead:


**Needs the user's approval (write: rewrites confidence/credibility/priority on every article):**

```bash

dc exec -T api python -c "from cti_core.celery_client import send_recompute_all; send_recompute_all()"
```

Option B: `POST /api/articles/confidence/recompute` as a `manage_intel` user (audit-logged). It runs
**inside the API request**, so on a large table it can hit the proxy timeout; prefer option A.

Expected: unassessed goes to 0. Duration: not measured on dev. **Projection**: minutes for a few
thousand articles (paging 500, one facts query per page).

### Rollback / if it goes wrong

- Application rollback is safe without touching the DB: the new columns are nullable/defaulted and
  unused by older code. `make deploy` auto-rollback restores the `:prev` images and never
  downgrades the DB.
- Optional DB downgrade (**write, needs the user's approval**, only after the app is back on 0.8.9):
  `dc run --rm migrate alembic downgrade c4f1a9d27e6b`. It drops the P6 columns, the index and
  `content_kind`; the computed scores are lost (they are recomputed on the next upgrade).
- `confidence_score` values are rewritten by the recompute; a rollback does **not** restore the old
  values. If needed, take them from the pre-deploy backup that `make deploy` writes.
- Recompute stuck or failing: check `dc logs worker | grep -i confidence`; re-run option A after the
  cause is fixed (idempotent).

### Known risks and follow-ups

- **Priority query cost.** `sort=priority` collapses per story with `row_number()` over the
  filtered set. Not measured on prod-sized data; after deploy run `EXPLAIN (ANALYZE, BUFFERS)` on
  the dashboard query (read-only) if "Perlu dibaca" feels slow.
- **Refresh watermark edge.** `confidence.refresh_stories` advances its Redis watermark
  (`cti:confidence:refresh_stories:watermark`) only after a successful run, taking the timestamp
  before the query; a story commit in flight across that boundary can be missed. The daily
  `recompute_all` (03:20) catches it. Members can be up to 10 min stale.
- **API start scan.** Every API start runs `EXISTS (... credibility IS NULL)` on `articles`. Cheap
  once every row is assessed (the first match ends it), but it scans the table while rows stay NULL.
- **Lower confidence downstream.** Values drop to 10-90: the newsletter ranking awards confidence
  points only above 50 (fewer articles get them, intended), and Splunk/STIX consumers see lower
  `confidence` values. Tell consumers before deploy.
- **Follow-ups:** read the live distribution (after-deploy checks 4-5) and record it in
  `docs/LLM_ASSIST_REDESIGN.md`; review the "Needs review" suggestions with an analyst.
